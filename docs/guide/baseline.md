# Baseline

Adopting Structura on an existing project usually reports hundreds of violations at once. A **baseline** records
the current violations so that the analysis only fails on **new** ones: you can enforce your rules today and pay
the existing debt back progressively.

## Generate the baseline

Declare the baseline file in `structura.php`:

```php
return static function (StructuraConfig $config): void {
    $config->addTestSuite('tests/Architecture', 'main');
    $config->baseline('structura-baseline.php');
};
```

Then record the current violations and commit the generated file:

```shell
php vendor/bin/structura analyze --generate-baseline
```

The path is relative to the configuration file. Without `baseline()`, the file is written to
`structura-baseline.php` beside the configuration, but it is only **used** once declared.

The generated file is a sorted PHP array, readable in code review:

```php
<?php

declare(strict_types=1);

// Generated by `structura analyze --generate-baseline`.
return [
    'Tests\\Architecture\\TestController::testDependencies' => [
        'src/Http/Controller/OrderController.php' => [
            'ToHaveMethod' => [
                'Resource App\\Http\\Controller\\OrderController must have method __construct',
            ],
            'ToNotDependOn' => [
                'Legacy\\Mailer',
            ],
        ],
    ],
];
```

## What is tolerated

From then on, `structura analyze` tolerates every violation recorded in the baseline and still reports the new
ones. The summary shows how many violations were tolerated:

```
Tests:    13 passed, 2 failed, 62 tolerated by baseline (15 assertion)
```

A violation is identified by its **test** (`TestClass::method`), its **file**, its **rule** (short class name) and the
**faulty element**
(the dependency, the trait, the constant…), never by its line:

- Editing a file does not invalidate its entries, even when lines move.
- Changing the configuration of a rule does not invalidate its entries: adding an allowed namespace to
  `toOnlyDependOn()` keeps the recorded dependencies tolerated.
- A new faulty element is reported: if `OrderController` depends on `Legacy\Mailer` in the baseline, a new
  dependency on `Legacy\Payment` fails the analysis.
- One entry covers a dependency, not each usage: a second usage of `Legacy\Mailer` in `OrderController` is still
  tolerated.
- An entry only covers its own test: if another test also forbids `Legacy\Mailer`, its violation is reported.
  Renaming a test class or method makes its entries stale and its violations new: generate the baseline again.

::: info
Rules reporting a **missing** element (`toHaveMethod()`, `toExtend()`, `toHavePrefix()`…) are identified by their
message, which contains the expected value: changing that value makes their entries stale and their violations new.
:::

Sources given with `fromRaw()` and custom rules written as anonymous classes cannot be identified across runs:
they are never recorded.

## Stale entries

When a violation is fixed, its entry no longer matches anything. The analysis reports it as a **warning**, without
failing:

```
Baseline entry Legacy\Mailer for ToNotDependOn in src/Http/Controller/OrderController.php from test Tests\Architecture\TestController::testDependencies no longer matches any violation
```

Run `--generate-baseline` again to remove stale entries, and commit the smaller file.

::: warning
A partial run may not execute every test, so it never reports stale entries: `--filter`, `--testsuite`,
`--stop-on-error`, `--stop-on-warning` and `--stop-on-notice`. For the same reason, `--generate-baseline` refuses
these options.
:::

In JSON output, the number of tolerated violations is `assertion_detail.tolerated`, and stale entries are listed in
`warnings`.
